# 玩家对象初始化与保存性别：2026-10-08 续审

结论：**已找到当前地图创建玩家对象时实际执行的角色初始化入口，但仍不能安全开放性别编辑。**两版 ROM 都从对象当前图像 ID 推断角色缓存 `0x02037078+7`；入口在性别反查前把 16 位图像 ID 截为低 8 位。V1.2 样本的覆盖图像 ID 为 `3599`（`0x0E0F`），实际反查收到的是 `0x0F`。隔离 CPU 中仅将 `SaveBlock2+8` 从 0 改为 1 再执行原生入口，缓存性别仍为 0，当前对象图像仍为 3599。另有游戏脚本可调用的例程直接读取保存性别，因此保存值与外观缓存可以分叉。

## 复跑与身份

新工具 `tools/audit_player_avatar_init.py` 只接受 `rom_versions.py` 的完整 SHA-256，并复核配置文件身份、地图初始化三段 Thumb `BL`、玩家对象移动类型分支、初始化跳板指针、图像截断指令、保存性别常量及脚本 special 表项。示例命令：`python tools/audit_player_avatar_init.py "path-to-ROM.gba" "path-to-state.ss1" --save "path-to-save.sav"`。`.sav` 可省略；工具不写入 ROM、即时状态、Flash 存档或运行中的 mGBA。每一矩阵行都新建 Unicorn 内存副本。

本轮使用两版精确 ROM、各自 `.ss1` 与 `.sav`，均通过。V1.0 SHA-256 为 `628607dcbeac3ab471310d5472c8fbd0df250745230207c488f66adbf1a43821`；V1.2 为 `b98d9701f4b567810c70221564c348f4482791c614c3f1bb282e96678b7a0896`。输入即时状态与 ROM 的配对来源仍由操作者保证。没有把本地私人文件路径、姓名、ID 或状态原始字节写入仓库。

## 实际地图入口

两版共有以下静态调用链：`0x08057106` 调 `0x0805EDF0` 初始化地图对象；循环内 `0x0805EE20` 调 `0x0805EE3C` 创建对象；对象移动类型 `+6 == 0x0B` 时，`0x0805EF60` 调 `0x0805F02C`。当前样本的玩家对象确实为该类型，位于 `0x02036E38 + 对象ID × 0x24`。`0x0805F02C` 是 ROM 跳板：V1.0 指向 `0x09D0D460`，V1.2 指向 `0x09D0F8E4`。这条链与上一审计中无直接调用的旧 `0x0805CA3C` 候选不同。

实际入口从对象取得图像 ID（V1.0 读取例程 `0x09D0D428`；V1.2 `0x09D0F8AC`），在入口 `+0x18` 以 `lsls r0,#24; lsrs r0,#24` 取低 8 位，然后调用性别反查（V1.0 `0x09D0D3CC`；V1.2 `0x09D0F850`），最后写到角色缓存 `+7`。反查例程内确有 `0x0300500C` 常量并可读取 `SaveBlock2+8`，但传入**完整**覆盖图像 ID 与原生入口传入**低 8 位**的结果不同。直接调用反查函数并不能代替执行原生入口。

| 隔离输入 | V1.0 缓存 `+7` | V1.2 缓存 `+7` | V1.2 对象图像结果 |
| --- | --- | --- | --- |
| 当前样本对象图像；保存性别 0 / 1 | 0 / 0 | 0 / 0 | 3599 / 3599 |
| 临时将对象图像设基础男性 0；保存性别 0 / 1 | 0 / 0 | 0 / 0 | 3599 / 3599 |
| 临时将对象图像设基础女性 7；保存性别 0 / 1 | 1 / 1 | 1 / 1 | 3599 / 3599 |

V1.2 当前图像 `3599` 若直接以完整 16 位传给 `0x09D0F850`，反查结果随保存性别 0/1 改变；原生入口实际传 `0x0F`，结果均为 0。隔离修改对象图像为基础女性 7 可使缓存成为 1，但初始化后 V1.2 对象图像又回到覆盖值 3599。这种临时对象改写既不证明屏幕精灵已安全重建，也不证明地图切换与存档重载会维持目标性别，**不能作为编辑事务方案**。

## 另一路保存性别消费者与劲敌边界

`0x0806C4F0` 的 Thumb 指针出现在游戏 special 表 `0x0815FC34`。两版隔离执行都证实它直接读 `SaveBlock2+8`，将 0/1 写到 `0x020370D0` 的 16 位结果；它不读取角色缓存。该路径可供脚本使用，说明剧情条件有独立读取保存性别的能力。本轮没有追到具体剧情脚本的调用位置或比较分支，不能断言哪些对白或事件实际使用它。

已知劲敌训练师 ID 329、426、438 在两版 `0x0823EAC8` 固定表中分别为类别 `0x51/0x59/0x5A`、队伍人数 4/4/6，队伍数据指针分别为 `0x0896F9D0`、`0x0823C7B0`、`0x0823CA20`。这些是 **ROM 固定记录**；故事脚本如何选择训练师 ID 及其是否依据保存性别、初始选择或其他变量，本轮未证。不能因姓名分支已核验而推断阵容联动已经解决。

两个版本的两份 `.sav` section 0 副本均在起始 8 字节与即时状态的玩家姓名字段一致，`+8` 性别也一致；签名和对首 `0xF00` 字节计算的校验值相符。这是现有数据的持久位置观察，没有对修改后保存、关闭重开或恢复做验证。

## 下一步接口与验收门槛

当前仅可增加只读状态诊断：同时显示保存性别、角色缓存性别、对象图像 ID、覆盖变量是否启用以及脚本 special 结果，并在不一致时提示。任何写入前须先追查对象图像扩展编码与 `0x0805F02C` 低 8 位截断的意图，找出本版真实的可重建路径；再追踪使用性别 special 的具体脚本与劲敌训练师 ID 选择；最后在独立游戏副本中覆盖步行、骑行、冲浪、地图切换、对白、对战、保存重载和条件恢复。现阶段没有已证实的“同步哪些字段并调用哪个刷新函数”接口。
