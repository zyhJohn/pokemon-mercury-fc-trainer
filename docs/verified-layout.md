## 宝可梦数据

队伍数量：`0x02024029`；队伍：`0x02024284`，每只 100 字节。

| 偏移 | 含义 |
|---|---|
| `0x00` | PID（32 位） |
| `0x04` | 原训练师 ID：TID + SID |
| `0x1C` | 形态还原物种编号（原版校验和位置已复用），保留现有值 |
| `0x1E..0x1F` | 保留现有值，不按原版重写头部 |
| `0x20` | 物种内部编号（不是全国图鉴号） |
| `0x22` | 携带道具 |
| `0x24` | 经验值 |
| `0x28` | 四槽 PP 提升次数，各两位 |
| `0x2C` | 四个招式，各 u16 |
| `0x34` | 四个当前 PP，各 u8 |
| `0x38` | 六项 EV，HP/攻/防/速/特攻/特防 |
| `0x48` | 六项 IV，各五位；bit30 是蛋、bit31 是隐藏特性 |
| `0x54` | 等级 |
| `0x56` | 当前 HP |
| `0x58` | 最大 HP，其后五项能力值 |

闪光公式：`TID xor SID xor PID低16位 xor PID高16位 < 8`。

PID 不是完整宝可梦的压缩 ID，也不是 IV 总和或校验码。闪光修改搜寻满足条件的 PID，保持性格 `PID % 25` 与低八位，因此保留通常的性别和普通特性奇偶选择。未知图腾还检查字形。晃晃斑默认拒绝改变PID；只有显式重新生成花纹时解除外观约束。

特性在本 ROM 中由隐藏标志和 PID 奇偶选择物种的三个特性槽。切换普通槽时搜寻保持性格、性别、闪光状态的 PID；仅可选该物种确实存在的槽位。修改 IV 必须保留同一 32 位字段的两个高位。

种族值表由 `0x080001BC` 的指针定位，记录大小 28 字节。招式表由 `0x080001CC` 的指针定位，记录大小 12 字节。本版读取到 `0x09DF58EB`。名称采用资料库，PP 上限采用本地 ROM 数值。修改招式会清除该槽 PP 提升次数，不清除其他槽。

## 合法性检查的边界

已实现的是本改版的结构、数值和派生能力值检查：IV 0～31；EV 单项 0～252、总和不超过 510；蛋标志一致；等级与 HP 范围；有效物种/特性槽；招式与 PP 边界；不重复配招。调整等级时同步经验门槛，调整物种、等级、IV、EV 时重算能力值。非濒死宝可梦默认保留已损失 HP，濒死状态保持。

**没有实现官方遭遇合法化**：未复原所有遭遇表、事件来源、PID/IV 随机生成关联、蛋招式/学习途径、闪光锁定、配信限制等。不能把“检查通过”解读为 PKHeX/官方交换合法，也不能用一个新 PID 自动证明合法。改版自身的特殊战斗模式及未识别机制仍需游戏内核对。

## 写入与恢复

### 经验表与 PC 压缩格式的追加核对

`GetLevelFromMonExp` 在 `0x0803E7C4`，其 `0x0803E828` 常量指向本 ROM 经验表 `0x09DFD8D4`。六条成长曲线的行跨度为 1024 字节。编辑器提取每条曲线 0～100 级的原始整数；**不要改回通用公式**：所有曲线的 1 级门槛为 1，起伏曲线 70 级为 276915，另外一些等级存在 1 点取整差异。隔离执行游戏函数发现并修正了这些差异。

PC 有 25 盒，每盒 30 格，每格 **58 字节**。`0x0808BA18` 跳转到 `0x09D54A44`，后者检查盒号 ≤24、槽号 ≤29，从 `0x09DD71AC` 的 25 项指针表取得各盒地址，以 58 为步长。盒子地址并非全部连续。

`0x09D54868` 将 58 字节转换为标准 80 字节 BoxPokemon。PID/OTID 在 0/4，物种 28，携带道具 30，经验 32，四个 10 位招式在 39～43，EV 在 44～49，IV/蛋/隐藏特性位在 54～57。等级由精确经验表推算。已开放 PID（闪光/性格/未知图腾）、IV、EV 和下述来源字段的定点编辑，保留其他压缩字节。**没有完整重编码器**，压缩头部、奖章等字段仍需补齐，不开放空槽创建及通用PC物种/招式编辑；0.2.11盒间移动复制完整已有记录，无需完整重编码器。

PC详情的实际解压映射：OT姓名20..26；亲密度/周期37；捕获球38完整字节；地点51；相遇等级52低7位；OT性别53 bit7。52 bit7及53低7位均保持不变。`tools/verify_pc_details.py`对179个非空槽共201组修改执行实际解压及取出转换，PID/OT/来源/蛋与特性标志一致；OT ID修改保留闪光和原有PID约束。未覆盖实机保存重载及PC实际取出。

537 次盒内编辑变体经过实际 ROM 解压函数及 `BoxMonToMon`（`0x0803E774`）验证，取出后的字段、等级与能力值全部一致。这些是隔离 CPU 中的游戏函数对照，仍非 mGBA 的实际保存/加载测试。

`tools/verify_rom_routines.py` 使用 Unicorn 在隔离内存执行上述 ROM 解压函数，将现有即时存档中 179 条非空盒内记录的 11 类主要字段逐一对照，全部一致。另执行实际 `CalculateMonStats`、`IsMonShiny` 与 `GetMonAbility`，核对 240 组队伍变体（包括 25 种性格）；1432 个物种的能力值与特性槽也通过对照。此测试不接触运行中的 mGBA，不代表真实 Lua 写入或保存加载已经验证。

### 招式来源证据

`0x08043E20` 指向等级招式指针表 `0x097C32B8`；各条目为三字节 `[u16 招式, u8 等级]`，以 `[0, 255]` 结束，等级 0 为进化招式。ROM 的 `0x09D41AF8` 返回等级招式对，每次最多 50 项。1432 个物种的提取结果与该函数的返回一致。

`0x08125A8C` 指向 128 项 TM/HM 招式表 `0x097E879E`，前 120 项为 TM，后 8 项为 HM。道具转学习器索引函数为 `0x09D3D852`，通过 `0x09D3D69E` 读取道具记录 **偏移 25** 的编号；非零减 1，零则使用 `(道具 ID - 289) & 255`。不能误用结构中偏移 40 的 secondaryId。ID341 → 索引122 → 招式57冲浪；ID342 → 索引123 → 招式70怪力。

`0x08043C68` 指向 `0x09400494`，每个物种 16 字节、128 位学习器兼容表。实际 `CanMonLearnTMHM` 入口 `0x08043C2C` 跳转 `0x09D3D9C4`，按四组 32 位掩码检查。界面只报告这些已知来源；未在等级表找到、或等级高于当前等级，都不能直接判为非法，因为学习器、遗传、进化前、教学和事件可能提供其他途径。

### 战斗状态

实际能力值函数 `0x09D073D6` 读取 `gMain + 0x439` 并检查 bit1；常量在 `0x09D07430` 和 `0x09D07434`，对应 `0x03003529` 的掩码 2。队伍写入要求此位为零，同时在 Lua 事务中比较读取时的完整字节，避免检查后进入战斗的竞态。特殊战斗规则的能力值不适用普通公式，所以战斗中保持只读。

### 事务行为

新版 Lua v3 协议 `BATCHCRC` 在同一回调内先检查 ROM CRC32、比较所有预期字节，再写入。比较包括 49 处 ROM 特征、SaveBlock 指针、队伍数量、战斗标志和被编辑对象；盒内写入增加 PC 格式特征。任一字节不符返回 `ERR stale`，CRC32 不符返回 `ERR rom`，均不写入。旧版直接 WRITE 和无 CRC 的 BATCH 指令不再支持。v1/v2 桥接在界面中仅可读取。

### 下一阶段新增字段

`GetMonData` 为 `0x0803FBE8`，`SetMonData` 为 `0x0804037C`。实际函数对照确认：亲密度/蛋周期 offset41；捕获球 offset42（完整字节，不是原版来源字中的4位）；地点offset69；相遇等级offset70低7位；OT性别offset71 bit7；OT姓名offset20..26；OT ID offset4..7。其余来源打包位保持原样。

玩家 SaveBlock2 指针 `0x0300500C`：姓名前8字节，公开/隐藏 ID 在 +10/+12。`GetCombinedOTId`（`0x080CC1E4`）实际读取这4字节；`StringExpandPlaceholders`（`0x08008FCC`）读取玩家姓名。英文字符参考 [引擎字符表](https://raw.githubusercontent.com/pret/pokefirered/master/charmap.txt)，与当前样本 `ee ed dc` 一致；中文编码已另行核对，见下节。主角性别 +8 仅只读，未开放写入。

主角性别追加研究：`ClearPlayerAvatarInfo`的常量确定场景角色缓存`0x02037078`，性别在缓存+7。实际图像入口`0x0805C808`跳到`0x09D0D320`并使用缓存；只改SaveBlock2+8不会更新此读数。改版通过`0x09D0D20C`读取变量501F/5020/5021/5022/503D/5023/5025覆盖部分外观；当前样本前五种状态分别返回2834..2838，不随显式性别改变。工具`audit_player_avatar.py`可复现。参考[原引擎角色逻辑](https://raw.githubusercontent.com/pret/pokefirered/master/src/field_player_avatar.c)定位，结论以本改版实际函数为准；场景精灵重建、地图切换、剧情选择及保存重载仍未验证，不开放性别写入。

图标指针表：`0x08097050` → `0x097BFC14`；调色板记录表 `0x080971F0` → `0x083D4038`；物种调色板索引表 `0x080971F4` → `0x097BF602`。图块为32×32、4bpp、512字节，调色板32字节。实际 `GetMonIconTiles`/`GetValidMonIconPalettePtr` 验证1432项。雌性图标映射从改版钩子核对，物种824的图标受运行状态影响，暂回退文字；蛋图标同样回退文字，闪光使用标记，未伪造闪光图标配色。

`GetUnownLetterFromPersonality`（`0x08082AB8`）与图标函数对照56组字形变体。28种本地图块经目视核对，0..25为A..Z，26为“!”，27为“?”；与参考百科给出的标点顺序不同。字形PID搜索保留约束，但不再固定整个低字节。PC 字形仅改PID，其余58字节数据保留。

晃晃斑正面花纹函数`0x08043458`使用`0x0825265C`的4条36字节掩码记录。实际改版前图描述符`0x097BBA40`指向LZ77图像`0x095F5B20`；普通/闪光调色板分别为`0x095F5DF4`/`0x094B0924`，以实际调色板函数核对。预览从当前ROM读取并解压，不分发图像。参考[原引擎花纹逻辑](https://raw.githubusercontent.com/pret/pokefirered/master/src/pokemon.c)定位，实际2048组普通/边界PID与合成颜色图块渲染对照一致。

花纹重新生成是显式操作，支持队伍和PC；PID搜索保留所选性格/闪光、原性别及适用普通特性奇偶。新候选避免首个斑点的Y偏移下溢，预览仅绘制64×64有效区域。默认普通编辑仍保护晃晃斑PID，不提供任意PID输入或完整来源合法化。

CRC32 为 `B4AF11C8`，使用 mGBA 0.10.5 的 `emu:checksum()`：源码 `src/core/scripting.c` 明确返回默认 CRC32 的四字节大端字符串；`src/gba/core.c` 返回模拟器加载 ROM 时记录的 `romCrc32`。它用于辨别加载文件版本，运行时另以指令特征与目标数据比较，不能视为密码学认证或任意热补丁检测。

每次写入先将原始数据与预期新数据保存到 `backups/`，成功后逐块读回核对。恢复备份也是比较后写入；游戏状态不再等于备份记录的新值时拒绝恢复，避免覆盖后续进度。网络中断或写后状态变化会标为 `failed-or-unconfirmed`，不能自动恢复。

范围比较能避免正常的帧间数据竞争，不保证底层 emu API 抛异常或进程崩溃时跨全部字节自动回滚。错误时应核对诊断和备份，不自动反复重试。

## 中文姓名编码（0.2.1）

字符编号与 [第三代字库补丁字符表](https://raw.githubusercontent.com/Wokann/Pokemon_GBA_Font_Patch/5a78e4da2cf61fbe7b7e64b110accc06cdee800b/pokeFRLG/PMRSEFRLG_charmap.txt) 的6763个双字节汉字逐项一致。按标准GB2312汉字顺序（B0A1至F7FE，跳过未定义项）排列，每247个字符换一行；游戏首字节为01至1E，跳过06和1B，第二字节为00至F6。实现从Python标准字符编码生成编号，不携带外部字符表或游戏字库。此编号不是把GBK或UTF-8字节直接写入。

本ROM的实际显示函数在 `0x0820F658`，入口补丁在 `0x08005842`，指针在 `0x08006920`。它先删除首字节编号中的保留行，再按256列（不是247列）计算字体地址，每个字形64字节。正常字体基址 `0x087D0000`，小字体 `0x08840000`。这与参考补丁的新1bpp字库实现不同，因此以本ROM实际函数为准。字形解压使用 `0x080068D4` 路径，输出到 `0x03003DA0`，小/正常字形宽10/12、高14。

`tools/verify_chinese_names.py` 在隔离CPU检查两套字体共13526次选择、30次字形解压，10个游戏物种名称，以及40组玩家名字占位替换、队伍OT读写和PC解压/取出姓名传递。另私下查看了抽样字形，图像不提交。真实菜单显示、存档重载仍待补验。

写入上限统一为7字节：汉字2字节、已支持英文等1字节。玩家姓名占8字节，最后保留FF终止符；OT存储占7字节，满7字节由GetMonData追加第8字节FF。因此最多3个汉字，也可以混合英文，总容量超出即拒绝，不截断。未知或不完整双字节序列仍返回未知并原样保留；只修改ID不重新编码姓名。

| 累计游玩时长 | SaveBlock2指针`0x0300500C`；+0xE小时u16，+0x10分钟，+0x11秒，+0x12帧计数 | 仅前4字节，0～999:59:59；保留帧计数 |
| 引擎每日刷新日期 | Var5009/500A；RAM `0x0203B386`，4字节；持久section4内`0xEDE` | 有效且处于未来时可预览调整到游戏日期前一天；无通用事件标志编辑 |

实际时钟转换`0x09D56A28`把BCD缓存写入上述gClock字段；星期读取`0x09D59704`取+5。对调只将小时加/减12，日期不变。游玩时长跳转入口`0x0805486C`指向`0x09D56AF4`，实际最大值函数`0x080548D4`写999、59、59、59；+0x12可为0xFF等待下一RTC秒，不能将它当作无效时长，或与时分秒一并用陈旧帧字节比较。0.2.10保留它，时长应用前读取最新旧值；`BATCHVERIFYCRC`在同次Lua回调比较所有旧值、写入、读回变化字段，再返回成功，避免下一网络请求前正常计时产生误报。时间事务额外使用7处可复现函数特征；没有扩大全局49处检查，保持原数值事务64项容量。

每日记录按低位起为minute6、hour5、day5、month4、year%100的7位、century5。实际`GetVarPointer(0x5009)`返回`0x0203B386`。未来日期判断`0x09D59350`按年/月/日比较；每日检查/更新`0x09D59410`对未来日期返回false，对今天也返回false，对过去日期返回true且可更新到今天。编码更新`0x09D59548`及每日刷新调用点`0x09D64C04`已核对；后者明确使用5009。源代码只是机制线索，地址和变量由本版ROM确认。序列化`0x09D56C48`把RAM `0x0203B240`起0x258字节放到section4的0xD98后，字段位于0xEDE；实际函数输出及最新`.sav`邻近36字节与即时存档吻合。

游戏的RTC持久设置在mGBA的`.sav`尾部，不在gClock或宝可梦记录：文件长度`0x20010`，前`0x20000`为游戏Flash；末16字节中0～6是BCD年月日星期时分秒，7是RTC控制位（本工具支持0x40/0x48的24小时模式），8～15为小端有符号64位`lastLatch`。mGBA读取时按当前系统本地时区`mktime`计算尾部日期的epoch，`offset = lastLatch - rtcTime`，采样时日历是`localtime(now - offset)`。指定日期写入目标BCD、派生星期及当前epoch；电脑校准写入实际当前日期和epoch，offset=0。仅改这16字节，因此不改变游戏存档扇区校验。无尾部、即时存档、未知模式、无效日期/范围拒绝；关闭游戏后独占文件、整文件旧值比较、完整备份/fsync、读回、整文件条件恢复。
