# 每日与星期事件：两版 ROM 有界核验（2026-10-08）

## 结论与可开放范围

目前只能确认通用每日日期判断、星期读取入口和一个使用每日判断的 ROM 入口，**不能把周日活动奖励或领取标志映射到 Var5009/500A，也不能开放批量清除标志**。已有时间页的未来日期修复仍以“把通用记录前移至昨天，让下一次游戏流程有机会刷新”为边界。V1.2 通用检查器对未来日期采取不同判定；这不否定现有界面事务的字节写入，但不能把 V1.0 的阻止刷新解释套到 V1.2，或据此宣称所有活动恢复。两版的具体周日内容是否重新出现仍需地图流程和保存重载验收。

本次只读使用完整 SHA-256 与 `rom_profile.json` / `rom_profile_v12.json` 核对的两版本地 ROM、各自 `.sav` 和 `.ss1`。原件没有写入；隔离 Unicorn CPU 中的 RAM 改动只在进程内。私人原始输入 SHA、存档内容比较及矩阵详见被 Git 忽略的 `diagnostics/daily-events-v10.json`、`diagnostics/daily-events-v12.json`。复现工具为 `tools/audit_daily_events.py`，要求显式传入 `ROM STATE --save SAVE --profile PROFILE --output diagnostics/REPORT.json`，不内置私人路径。

例如：`python tools/audit_daily_events.py <ROM.gba> <STATE.ss1> --save <SAVE.sav> --profile rom_profile.json --output diagnostics/daily-events-v10.json`。V1.2 改用对应配置与输出名。

## 实际指令与记录映射

| 对象 | V1.0 | V1.2 | 已证实作用 |
| --- | --- | --- | --- |
| 完整 ROM SHA-256 | `628607dcbeac3ab471310d5472c8fbd0df250745230207c488f66adbf1a43821` | `b98d9701f4b567810c70221564c348f4482791c614c3f1bb282e96678b7a0896` | 精确版本门槛 |
| 日期变量 | `0x5009/0x500A` → `0x0203B386` | 同左 | 4 字节打包日期；Flash section 4 内偏移 `0xEDE` |
| 未来检查器 | `0x09D59350` | `0x09D5D4C8` | 返回记录日期是否晚于当前日期 |
| 通用每日检查器 | `0x09D59410` | `0x09D5D6D0` | 参数 1 为 0 仅查询，为 1 时在允许状态写回当前日期 |
| 日期编码更新器 | `0x09D59548` | `0x09D5D648` | 由检查器路径使用 |
| 星期 getter | `0x09D59704` | `0x09D5D8B8` | 从 `gClock+5` 读出周日 0～周六 6；在特殊函数表 `0x081600C8`，索引 `0xDA` |
| 每日检查入口 | `0x09D64C04`，由 `0x09D4C3CE` 调用 | `0x09D68FD8`，由 `0x09D4F64E` 调用 | 指令加载 `0x5009`，以参数 0 调用检查器，随后走自己的结构更新逻辑；尚无具体活动名称或领取 flag 的可靠映射 |
| 另一检查器调用 | `0x09D63208` | `0x09D675AC` | 同样使用 `0x5009`；周边代码有自己的条件和数据更新，不能据此推定所有活动共用该变量 |

`tools/audit_daily_events.py`逐字节核查每日入口的 LDR 字面量、Thumb BL 目标、星期表槽和 `GetVarPointer(0x5009)` 的实际 RAM 返回值。全 ROM 对相关函数的 Thumb BL 扫描列在私人报告中；扫描结果只是候选调用点，数据区域也可能碰巧具有相同字节，必须结合指令上下文。星期 getter 没有找到直接 BL；表槽说明脚本可以通过特殊函数调用它，**不证明周日活动确实调用**。

## 实际 ROM 跨日／跨周矩阵

每版在隔离 CPU 执行 6 种日期转换 × 查询/更新两种模式，共 12 组；同时验证星期值、未来判定和变量邻近字节不变。

| 记录日期 → 当前日期 | V1.0 允许 | V1.2 允许 | 参数 1 的记录结果 |
| --- | --- | --- | --- |
| 2026-10-03 周六 → 10-04 周日 | 是 | 是 | 当前周日 |
| 2026-10-04 周日 → 10-05 周一 | 是 | 是 | 当前周一 |
| 2026-10-04 周日 → 当天 | 否 | 否 | 不变 |
| 2026-10-05 周一 → 10-04 周日（未来记录） | 否 | 是 | V1.0 保留未来周一；V1.2 写回周日 |
| 2024-02-29 → 03-01 | 是 | 是 | 当前日 |
| 2026-12-31 → 2027-01-01 | 是 | 是 | 当前日 |

参数 0 的所有组均保留原记录。以上只证明通用函数对合成日期的行为。进入地图时脚本何时运行、玩家此前是否领取、NPC/场景如何显示，都不在隔离 CPU 覆盖内。

未来记录这组中，两个版本的 `future_checker` 均返回真。V1.0 的 `checker(0x5009, 0)` 和 `checker(0x5009, 1)` 均返回假，记录不变；V1.2 两种模式均返回真，只有参数 1 会把记录写回当前日。每日入口 `0x09D64C04` / `0x09D68FD8` 明确以参数 0 调用，因此它自己只查询，不直接写回通用日期。

## 原始样本与未解决项

本次 `.sav` 和 `.ss1` 的 section 4 日期及邻近字节在两版都不一致，因此这些输入不是可用来证明同一次保存重载的配对快照。V1.0 `.sav` 的通用记录为 2026-10-06，`.ss1` 为 2026-09-30；V1.2 分别为 2026-10-19 和 2026-10-16。不能拿其中一个时间点的 RTC 与另一个时间点的活动状态推断刷新成败。

具体每日/周常事件、周日内容入口和对应 flag/var **仍未定位**。下一步需要在相同存档副本中记录周六、周日、周一各活动 NPC 的地图/对话/领取状态及游戏内保存重载，再对已命名事件逐条追踪脚本调用和 flag 写入；期间保留领取位原值，不试探性清除。玩家此前报告“改后仍显示周日内容”的现象不能由本次矩阵单独解释，也不能宣称已修复。
